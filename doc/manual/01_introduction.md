# Introduction {#introduction}

This chapter says what LiteSPI is, why it exists, what it does and what it does not do. It gives
the status of each part, the layout of the repository and a map of the manual. Every reader should
start here.

## What the project is {#intro-what}

LiteSPI connects an FPGA design to a SPI flash or another SPI memory. It reads the flash as if it
were memory, so that a CPU can fetch data and run code from it. It also lets software send any
command to the chip, to identify, erase and program it. Most FPGA boards boot from such a flash,
so the same chip can hold the bitstream, the firmware and user data.

The project has four parts, shown in the figure below. The PHY drives the pins of the flash. The
MMAP turns bus reads into flash read commands. The master lets software build any command through
registers. The crossbar shares the PHY between the two frontends.

![LiteSPI at a glance. The CPU reads the flash through the MMAP on the Wishbone bus and sends
other commands through the registers of the master; the crossbar gives the PHY to one frontend at
a time; the PHY drives SCK, CS and the data lines of the flash.](intro_overview.svg)

The gateware is written in Python with Migen and LiteX, and generates Verilog for the FPGA tools.
It is used as a LiteX library, usually through the `add_spi_flash` method of a LiteX SoC, or as a
standalone Verilog core generated by `litespi_gen` (see [Integration in a LiteX
SoC](#integration)).

## Why LiteSPI {#intro-why}

Every FPGA board has a SPI flash, but each FPGA family reaches it differently. On some boards the
flash clock is a regular pin; on others it is the configuration clock pin, reachable only through
a vendor primitive. LiteSPI hides this in the PHY: the same core runs on every family, and only the
PHY picks the I/O primitives and the clock path.

The flash appears in the address map of the SoC, as the figure below shows. The CPU reads it like
a ROM, and a CPU can execute code from it in place (XIP). Small FPGAs use this to run the LiteX BIOS
from the flash and keep their block RAM for data.

![The flash in the SoC address map. The `spiflash` region, the size of the flash, is served by the
MMAP next to ROM, SRAM and main RAM; the registers of the PHY, the MMAP and the master sit in the
CSR region.](intro_soc.svg)

Software keeps full control of the chip. At boot, the LiteX BIOS enables the quad mode, tunes
the SCK frequency of the SDR PHY and measures the read speed; its console offers
commands to erase and program the flash ([BIOS, boot and flash update](#software)).

The chips themselves are described once, in a database of 482 SPI memories: 481 NOR flashes and
one SPI PSRAM. Each class gives the size, the page size, the supported commands and the dummy cycles
of one chip, so a design names its flash instead of configuring the core by hand
([The SPI memory database](#modules)).

## Features at a glance {#intro-features}

| Area | Features |
|--------------------|------------------------------------------------------------------------|
| PHYs | SDR PHY on any FPGA with SCK divided from the system clock; 1:2 PHY with SCK at its own clock (the system clock by default) through DDR I/O registers; STARTUPE2 (Xilinx 7-Series) and USRMCLK (Lattice ECP5) clock paths; STARTUPE3 I/O path (Xilinx UltraScale+) |
| Widths | x1, x2, x4 and x8 data lines; command, address and data phases each at their own width |
| SPI modes | SPI mode 0 and SPI mode 3, selected by a register of the SDR PHY |
| Clock | SDR PHY: SCK divisor set at build time and changed at run time by a register; 1:2 PHY: SCK at the PHY clock, no divisor; separate SPI clock domain optional |
| MMAP | Wishbone slave for reads, bursts of sequential words under one command, programmable dummy cycles, writes for SPI RAM |
| Master | Register access to any command: chip select, length, width and output enable of each transfer, FIFOs, optional interrupt |
| Sharing | Crossbar between the MMAP and the master, several chip selects |
| Database | 482 SPI memories with their sizes, opcodes, dummy cycles and quad enable method; an optional erase geometry |
| Software | LiteX BIOS: quad enable, QPI entry, SCK calibration, read speed test, erase and program commands, boot from flash |
| Integration | LiteX library (`add_spi_flash`, `add_spi_ram`), or standalone Verilog core from `litespi_gen` |
| Verification | Unit tests, pin-level flash model driven by the real PHY, stream-level PHY model for `litex_sim` |

## Status {#intro-status}

The table below gives the status of each part of LiteSPI. It is the only status table of the
manual: the other chapters link to it.

| Part | Scope | Status |
|-------------------------|--------------------------------------------|------------------------|
| SDR PHY | `rate="1:1"`, any FPGA family | Validated on hardware |
| 1:2 PHY | `rate="1:2"`, FPGA DDR I/O registers | Validated on hardware |
| x1 reads | Mode 1-1-1 | Validated on hardware |
| x4 reads | Modes 1-1-4 and 1-4-4 | Validated on hardware |
| MMAP reads | Memory-mapped reads and XIP | Validated on hardware |
| Master | Register access to any command | Validated on hardware |
| STARTUPE2 | Xilinx 7-Series, flash clock on CCLK | Validated on hardware |
| USRMCLK | Lattice ECP5, flash clock on MCLK | Validated on hardware |
| STARTUPE3 | Xilinx UltraScale+ (`LiteSPIXilinxUSPHY`) | In development |
| MMAP writes to flash | `with_mmap_write="csr"` | In development |
| SPI RAM | `add_spi_ram`, SPI PSRAM | In development |
| QPI | Mode 4-4-4 | In development |
| Octal | x8 modes | In development |

*Validated on hardware* means that the maintainers state that the part works on real boards.
Numbers, such as a read speed, are given only where a public commit or document records them.
*In development* means that the code is in the repository but not yet validated on hardware: use
it, but expect to debug it.

The parts not listed, such as the dual (x2) reads, have code and simulation tests but no recorded
hardware status. [Supported FPGAs and boards](#boards) lists the families and targets that use
each PHY.

## Who uses it {#intro-users}

LiteSPI is the SPI flash core of LiteX: `add_spi_flash` instantiates it, and the LiteX BIOS drives
it. The target scripts of LiteX-Boards call `add_spi_flash` on 75 targets, from small iCE40
boards to Kintex-7 and UltraScale+ boards, on Xilinx, Lattice, Gowin, Efinix, Cologne Chip and
Altera FPGAs. 25 of the 28 Xilinx 7-Series targets reach the flash through STARTUPE2 and all 9
Lattice ECP5 targets through USRMCLK; on 19 targets, the LiteX BIOS itself runs from the flash.

`litex_sim --with-spi-flash` adds it to the LiteX simulation, with a model of the PHY and of the
flash contents ([Simulation and tests](#simulation)).

## What it is not {#intro-limits}

LiteSPI drives SPI memories from an FPGA. It does not implement the features that are not needed
for that, and some neighbouring interfaces are out of its scope:

- No double transfer rate (DTR) on the flash side and no octal DTR (OPI). The database lists the
  DTR opcodes, but both PHYs refuse a module configured for them.
- No discovery: LiteSPI does not read the SFDP tables of the flash. The module class describes the
  chip, chosen when the design is built.
- No prefetch and no cache in the core. The MMAP clocks a word out of the flash only when the bus
  asks for it; a CPU cache or the L2 cache of LiteX goes in front when needed.
- No continuous read mode: the MMAP drives no mode bits and keeps CS low between sequential reads
  instead ([Memory-mapped reads and writes](#mmap)).
- No HyperBus or OctaBus memory: LiteX has a separate HyperRAM core.
- No SPI slave and no generic SPI peripheral master. LiteX provides both, as `SPISlave` and
  `SPIMaster` in `litex/soc/cores/spi/`, for sensors, converters and other SPI devices.

LiteX also holds two older flash cores, `litex/soc/cores/spi_flash.py` (register access only, for
7-Series, UltraScale and ECP5) and `litex/soc/cores/spi_opi.py` (octal DTR on 7-Series). They are
separate from LiteSPI and not covered by this manual.

## Repository layout {#intro-layout}

| Path | Content |
|-------------------------------------------------|-------------------------------------------------|
| `litespi/__init__.py` | The `LiteSPI` wrapper: crossbar, MMAP and master, clock domain crossing |
| `litespi/core/` | The frontends: `mmap.py` (MMAP), `master.py` (master) |
| `litespi/crossbar.py` | The crossbar between the frontends and the PHY |
| `litespi/phy/` | The PHYs: generic SDR and 1:2, Xilinx and Lattice backends, simulation model |
| `litespi/clkgen.py` | SCK generators of the SDR and 1:2 PHYs |
| `litespi/cscontrol.py` | Chip select control: minimum CS high time |
| `litespi/common.py` | Stream layouts between the core and the PHY |
| `litespi/modules/` | The SPI memory database: NOR flashes (`modules.py`), SPI RAM (`ram_modules.py`) |
| `litespi/spi_nor_flash_module.py` | Base class of the modules: read mode, dummy cycles, erase geometry |
| `litespi/opcodes.py`, `ids.py` | Opcodes of SPI NOR flashes, manufacturer identifiers |
| `litespi/flash_model.py` | Pin-level SPI NOR flash model for simulation |
| `litespi/gen.py` | The standalone generator `litespi_gen` |
| `test/` | Unit and simulation tests |
| `doc/` | This manual (`doc/manual/`) and its figures (`doc/diagrams/`) |

The software is not in this repository: the BIOS code that drives the flash is in
`litex/soc/software/liblitespi/` of the LiteX repository, and `add_spi_flash` in
`litex/soc/integration/soc.py`.
